Section B

Memory and leaks

Opening and closing the watchlist ten times adds 60 MB that is not given back, and after five minutes the app holds 380.5 MB. The watchlist cubit lives for the whole app session, and the code adds objects to it or to long-lived streams on every open and every list update without removing them: stream subscriptions and tooltip controllers per row, a new StreamController per build, keys that force every row to be rebuilt from scratch, a listener in the indices rail and an ever-growing symbol list. These changes release what each open creates, without changing what the user sees.

B1

Cancel row tooltip subscriptions and dispose controllers

Every WatchlistItem listens to the cubit's tooltip stream in initState and never cancels, and creates three JustTheControllers it never disposes. Keep the subscription, cancel it in dispose and dispose the controllers.

Teams FERisk LowEffort S · ≤ 1 dayNo visible change

Today

initState calls watchlistCubit.toolTipSteamSubscription.stream.listen(...) and drops the subscription. dispose() only calls super.dispose(). The cubit is app-scoped (apps/super_app/lib/Investor/core/utils/trader_bloc.dart line 90), so each disposed row stays referenced by the stream's listener list until that StreamController is replaced, and its three JustTheControllers (ValueNotifiers) are never disposed. With B3 rows are disposed and recreated on every list update, so this repeats many times per open.

What to change

  1. Add StreamSubscription<bool>? _tooltipSub; assign it in initState.
  2. In dispose: _tooltipSub?.cancel(); for (final c in tooltipController.values) c.dispose(); then super.dispose().
  3. Do not call setState or hideTooltip after dispose (the listener checks mounted).

B2

Create the tooltip stream once per listing and close it

WatchlistListing replaces the cubit's tooltip StreamController with a new one on every build and never closes the old one. Create it once in initState, close it in dispose.

Teams FERisk LowEffort S · ≤ 1 dayNo visible change

Today

build() runs watchlistCubit.toolTipSteamSubscription = StreamController<bool>.broadcast(); on every build. Builds happen on every list update, theme stream event and parent rebuild. The old controller is never closed, and its listeners (rows from B1) keep it and the rows alive until the rows are collected.

What to change

  1. In initState (after super.initState), read the cubit with context.read<WatchlistCubit>() in a post-frame callback or didChangeDependencies once, create the controller and keep a reference.
  2. Remove the assignment from build().
  3. In dispose(): close the controller only if it is still the one this listing created.

B3

Keep list and row keys stable across rebuilds

The listing creates a new GlobalKey for the list and for every row inside build, which forces Flutter to throw away and recreate every row subtree on each list update. Create the keys once and reuse them.

Teams FERisk MediumEffort S · ≤ 1 dayNo visible changeDepends on B1

Today

build() does var listViewKey = RectGetter.createGlobalKey(); and itemBuilder does _keys[index] = RectGetter.createGlobalKey(); before wrapping the row in RectGetter(key: ...). A widget with a different key cannot update the existing element, so on every listing build the whole RefreshIndicator/ListView subtree and every visible row (Slidable, StreamBuilder, WatchlistItem state, three tooltip controllers, one stream subscription) is unmounted and mounted again. One open of Bench 20 emits WatchlistListLoaded at least twice (cache, then network; more with sort), so this happens several times per open.

What to change

  1. Make final GlobalKey<RectGetterState> _listViewKey = RectGetter.createGlobalKey(); a field; pass it where listViewKey is used.
  2. In itemBuilder: final key = _keys.putIfAbsent(index, () => RectGetter.createGlobalKey());
  3. In build, remove keys whose index >= watchistScrips.length so getVisible never indexes past the list (today a stale index would throw inside the try and return an empty list).
  4. Keep the ValueKey(index) on the InkWell and the Key(scripCode) on Slidable unchanged, so a sort still resets each row's swipe state.

B4

Release the screen context held by the cubit

The app-scoped WatchlistCubit stores the screen's BuildContext on every build and keeps it after the screen is disposed. Clear it in the screen's dispose.

Teams FERisk LowEffort S · ≤ 1 dayNo visible change

Today

build() calls cubit.saveContext(context) (watchlist_screen.dart 530). The cubit outlives the screen (provided in trader_bloc.dart), so after the user leaves the Watchlist tab it still references the defunct element of the last WatchListScreen until the next open replaces it.

What to change

  1. Add void clearContext(BuildContext c) { if (identical(_context, c)) _context = null; } to WatchlistCubit.
  2. Call it in WatchListScreen.dispose() before super.dispose().
  3. Check the two places that use _context! (fetchWatchlist and getWatchlistById error paths): they run only when shouldShowToast is true, which requires _context?.mounted.

B5

The indices rail in the watchlist header adds a listener to the indices list on every mount and never cancels it. Keep the subscription and cancel it in dispose.

Today

initState runs cubit.mappedIndices.stream.asBroadcastStream().listen((event) { safeSetState(...); subscribeGlobal(...); }) and dispose() does not cancel it. ExploreIndicesCubit is long-lived, and the watchlist screen (and its header) is remounted on every bottom-nav visit, so every visit adds one more listener holding a disposed State. safeSetState skips setState when unmounted, but subscribeGlobal still runs for every stale listener when the indices list changes.

B7

Find the rest of the growth with a memory diff

Part of R9 and the two R2 memory states are not explained by Dart code: the R2 dumps show Java heap of about 25 MB in the low runs and about 94–102 MB in the high runs, and a WebView exists in-process. After B1–B6, take a DevTools memory diff and an Android heap dump across 10 open/close cycles.

Teams FERisk LowEffort S · ≤ 1 dayNo visible changeverify on deviceDepends on B1 B2 B3

Today

Each open of the Watchlist tab runs initState again (the shell does not keep the page alive), starts a fetch with a loading state, logs analytics and mounts the header. The R9 run was manual and at market close, so live-tick objects were not part of it. The Java heap difference between R2 runs points at native/Java SDK objects (WebView or analytics SDKs), which Dart tooling will not show.

What to change

  1. Profile build, DevTools Memory: snapshot after first open, after 10 open/close cycles, diff by class (look for WatchlistItem states, JustTheController, StreamController, _StreamBuilderBaseState, CommonIndicesShowState).
  2. adb shell dumpsys meminfo com.mosl.mobile before/after; Android Studio heap dump for Java objects (WebView, CleverTap, MoEngage, Plotline).
  3. Record which objects grow; open a follow-up change for anything outside this module.
