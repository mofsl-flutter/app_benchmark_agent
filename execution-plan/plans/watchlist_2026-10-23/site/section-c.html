Section C

Scrolling and frame delivery

Scrolling the watchlist is free of jank (0.34 % janky frames, p99 15 ms), but on the 120 Hz screen only 75.3 frames per second reach the display, about 63 % of what the screen offers. The code shows that every frame of a downward scroll rebuilds the whole header, that the whole screen rebuilds on each list update, and that the list re-measures itself. The app also renders through a texture view on Android 11 and later, which adds a second composition pass. These changes remove per-frame work and test the render mode behind a flag.

Change details

C1

Emit the header pin state only when it changes

On every frame of a downward scroll the listing calls togglePersistHeader(false), which emits a new state and rebuilds the whole header (landing header, wealth tile, indices rail, tab bar, banners). Emit only when the value actually changes.

Teams FERisk LowEffort S · ≤ 1 dayNo visible change

Today

The NotificationListener in the listing calls watchlistCubit.togglePersistHeader(false) for every ScrollUpdateNotification while the user scrolls down (and for every ScrollUpdateNotification in heatmap view). togglePersistHeader always calls safeEmit(TogglePersistHeader(...)); WatchlistState classes have no == and safeEmit does not dedupe, so Bloc emits each time. The header BlocBuilder (watchlist_screen.dart 588-597, buildWhen: current is TogglePersistHeader) then rebuilds watchlistHeaderAppBar, which rebuilds the landing header, CommonIndicesShow (with new tick streams, A6), the curve tab bar and CrossSellingBanners, once per frame.

What to change

  1. In togglePersistHeader: if (_shouldPinnedHeader == shouldPersist && state is TogglePersistHeader) return; then assign and emit.
  2. Keep the first emit (from initState) so the header BlocBuilder still gets a TogglePersistHeader state.
  3. Add K3 (unit test: one emit per value change).

C2

Teams FERisk MediumEffort S · ≤ 1 dayNo visible changeverify on deviceDepends on C1

Today

buildWhen returns true for WatchlistListLoaded, WatchlistInitial and ToggleTabView. One open emits WatchlistListLoaded at least twice (cache result, then network result; more with sort or a default-watchlist refetch), and each one rebuilds the whole NestedScrollView and header before the inner list BlocBuilder (lines 985-990) rebuilds the list again. _body only passes the state through; the list content comes from the inner builder (verify there is no other reader).

What to change

  1. Search _body and its children for reads of the outer `state` other than ToggleTabView index; there should be none.
  2. Change buildWhen to current is WatchlistInitial || current is ToggleTabView.
  3. Keep the Comm. List and Option List branches unchanged (they do not depend on WatchlistListLoaded).

C4

Resubscribe only when the visible rows change

At every scroll end, and at every scroll-metrics change at the top, the listing walks all row keys, builds the visible symbol list and sends a subscribe request, which the broadcaster also writes to its log. Do it only when the visible set differs from the last one.

Teams FERisk LowEffort S · ≤ 1 dayNo visible changeDepends on B3

Today

On ScrollEndNotification or isFirstScroll(notification) (any ScrollMetricsNotification with extentBefore == 0) the listener calls getVisible, which reads every row's rect through its GlobalKey, then startQuoteStreaming(subscriptionList). In the broadcaster, subscribeQuote writes 'Subscribe Quote: <all symbols>' to the app log and computes subscription diffs (mosl_broadcaster broadcast_controller.dart 248-258) every time.

What to change

  1. Keep Set<BroadcastSymbol> _lastVisible in the state.
  2. After computing subscriptionList, if setEquals(_lastVisible, subscriptionList.toSet()) return; else store and call startQuoteStreaming.
  3. Clear _lastVisible when the watchlist changes (didUpdateWidget with a different watchlistInfo.id) so a new list always subscribes.

C5

Test SurfaceView rendering on Android 11+

MainActivity forces RenderMode.texture on Android 11 and later. Texture mode copies each Flutter frame into a texture that the Activity's own view hierarchy then composites, which matches the benchmark seeing RISE frames under ViewRootImpl and only ~63 % of 120 Hz frames delivered while frame times are low. Add a flag that selects RenderMode.surface and A/B it.

Teams FE · sharedBERisk HighEffort M · 2–4 daysNo visible changeverify on device

Today

getRenderMode() returns RenderMode.surface only for SDK <= Q and RenderMode.texture otherwise, overriding the manifest's surface value. The test phone runs Android 17, so RISE renders through a FlutterTextureView. The benchmark notes show RISE frames attributed to VRI-com.mosl.mobile/MainActivity, 75.3 fps at a granted 120 Hz, S1 0.34 % and p50 6.3 ms: frames are fast but not every vsync produces a displayed frame (verify with a SurfaceFlinger trace in both modes).

What to change

  1. Kotlin: read a boolean from FlutterSharedPreferences in getRenderMode(), the same way PushFanoutFlags.kt already reads a Remote Config value written by push_fanout_remote_config_service.dart; SDK <= Q keeps surface; SDK > Q returns surface only when the flag is true.
  2. Dart: after Remote Config fetch/activate, persist the flag for the next launch.
  3. Internal build: compare S5, S1, U4 and C1 on the OPPO in both modes; check WebView chart, payment and KYC SDK screens, screenshots/FLAG_SECURE, split screen and keyboard insets.
  4. Roll out only if S5 improves and crash-free sessions stay flat.
