Section G

Opening the watchlist (not measured yet)

The benchmark has not measured screen opening times yet (L2–L14 are empty), so this section has no today values. The code shows three things that add time on every visit to the Watchlist tab: the MTF list is awaited before the watchlist request starts, fixed 300 ms waits follow every sorted load, and a shimmer replaces the list on every visit even though the app-scoped cubit still holds the last list. These are worth fixing once L-timings exist to confirm the gain.

Change details

G1

Start the watchlist request without waiting for MTF

fetchWatchlist awaits getMtfStockList() before it starts the watchlist API call, although the MTF list is only needed to tag rows. Start both together and tag rows when the MTF list arrives.

Teams FERisk MediumEffort S · ≤ 1 dayNo visible changeverify on device

Today

fetchWatchlist emits the loading states, then await getMtfStockList() (UserManager call), then calls repository.fetchWatchlist. The two calls are independent, so the watchlist call waits for the MTF call every time the tab opens.

What to change

  1. final mtfFuture = getMtfStockList().catchError((_) {});
  2. Start repository.fetchWatchlist(...) as today.
  3. In the .then handler, await mtfFuture before _parseWatchlistRes so the first full emit has tags; the cache callback can emit without waiting.

G2

Remove fixed 300 ms waits after sorted loads

When a sort is saved, sortWatchlistDetail asks for a snapshot and then sleeps 300 ms before reading prices, and the parse paths add further 300 ms sleeps between emits. Sort with the cached prices immediately and re-sort when the snapshot arrives.

Teams FERisk MediumEffort M · 2–4 daysNo visible changeverify on device

Today

sortWatchlistDetail calls helper.fetchSnapShot(symbolSet) and then await Future.delayed(300 ms) before reading getBroadcastResponse for each scrip. checkWatchlistSorting calls it for every emit when a sort is active, and _parseWatchlistRes / _parseWatchlistByIdRes add further 300 ms delays after the first sorted emit. A user with a saved sort waits at least 300 ms more per load, and more when several emits are chained.

What to change

  1. Remove the delay in sortWatchlistDetail; sort with current cache values.
  2. Listen once (first event per symbol set, with a 1 s timeout) to the quote stream after fetchSnapShot and re-emit the sorted list if the order changed.
  3. Remove the 300 ms delays at lines 1455, 1554 and 1596.

G3

Show the last list instead of a shimmer on return

Every visit to the Watchlist tab emits WatchlistLoading first, so the list is replaced by a shimmer although the app-scoped cubit still holds the last list. When it already has scrips for the selected watchlist, render them and refresh in the background, behind a flag.

Teams FEProductRisk MediumEffort S · ≤ 1 dayVisible to usersverify on deviceDepends on A1

Today

initState calls _loadData, which calls fetchWatchlist(id, true); showLoading emits WatchlistHeaderLoading and WatchlistLoading, and the list builder returns WatchListShimmer for WatchlistLoading. The cubit is provided once for the app (trader_bloc.dart 90) and keeps watchlistList and watchlistScrips between visits.

What to change

  1. In fetchWatchlist: if (showLoading && WatchlistPerfFlags.keepListOnReopen && watchlistScrips.isNotEmpty) emit WatchlistLoaded and WatchlistListLoaded from the current fields instead of the loading states.
  2. Keep the cache callback and network refresh as today.
  3. Logout only calls WatchListScreen.resetSessionState() (apps/super_app/lib/main_common.dart 935), which resets tab state, not the cubit lists. Confirm whether the app-level BlocProviders are recreated on login; if not, clear watchlistList and watchlistScrips on logout before enabling the flag, so a second client never sees the first client's list.
