Watchlist Module Change Plan

A detailed, file-by-file plan to make the watchlist tab (bench 20 list, list tabs, manage stocks, create new watchlist, add-scrip search, list menu) faster, lighter and more reliable without changing what it does today. Every change lists the files and lines, the current code, the proposed code, which teams are involved, its risk to existing functionality, how existing behaviour is kept, what QA must re-test, and the expected result.

Sections

Each section page has a measured summary, a change table, and a full card per change with current and proposed code.

AIdle CPU and redraw on the watchlist

With nobody touching the phone, the Bench 20 watchlist keeps about two CPU cores busy and redraws about 40 times a second, and half of those frames are identical to the one before. The code shows three sources: every price packet rebuilds a whole row even when the shown numbers did not change, the header wealth tile rebuilds on every holdings tick and animates every 3 s, and new tick streams are created on every build. These changes keep every price, colour and animation the user sees, but stop the work that draws the same pixels again.

7 changes4 low · 3 med · 0 high
BMemory and leaks

Opening and closing the watchlist ten times adds 60 MB that is not given back, and after five minutes the app holds 380.5 MB. The watchlist cubit lives for the whole app session, and the code adds objects to it or to long-lived streams on every open and every list update without removing them: stream subscriptions and tooltip controllers per row, a new StreamController per build, keys that force every row to be rebuilt from scratch, a listener in the indices rail and an ever-growing symbol list. These changes release what each open creates, without changing what the user sees.

7 changes6 low · 1 med · 0 high
CScrolling and frame delivery

Scrolling the watchlist is free of jank (0.34 % janky frames, p99 15 ms), but on the 120 Hz screen only 75.3 frames per second reach the display, about 63 % of what the screen offers. The code shows that every frame of a downward scroll rebuilds the whole header, that the whole screen rebuilds on each list update, and that the list re-measures itself. The app also renders through a texture view on Android 11 and later, which adds a second composition pass. These changes remove per-frame work and test the render mode behind a flag.

5 changes2 low · 2 med · 1 high
DLive prices and returning to the app

On the watchlist, RELIANCE's price changed 17 times a minute, always on whole seconds, and after a minute in the background the app came back showing old prices for about a second before they moved. The client code passes every packet straight to the rows (no throttle), so the 1 s cadence most likely comes from the feed and needs a BE answer. The stale prices on return come from the socket being closed 15 s after the app is paused, so it must reconnect and log in again. One change is a BE question, the other a configurable socket delay; the visual 'updating' marker is E2.

2 changes1 low · 1 med · 0 high
EOffline and reconnect

When the network drops, the watchlist keeps its prices on screen (good) but gives no sign that they are old: no banner, no timestamp, and the prices look exactly like live ones. The only offline message in the code is a snackbar that is gated on a bottom-bar index the RISE shell does not seem to set. An offline cold start stops at the mPIN screen with a generic error. These changes add an in-screen offline banner and a stale marker behind flags, fix a listener that stops after the first trip to the background, and put the cold-start question to Product.

4 changes1 low · 2 med · 1 high
FRelease logging and privacy

While the benchmark created Bench 20, the release build wrote the client code and analytics attributes to logcat, a doubled API URL, and an 'API Failed' line for a successful call. The code shows where each comes from: plain print calls in the CleverTap helper, a log line placed before parsing every API response, a URL built from an origin plus a path that is already a full URL, and a print of every cached response. The same paths also spend CPU converting whole responses to strings. These changes keep analytics and the app's own file log working but stop writing user data and noise to logcat.

9 changes9 low · 0 med · 0 high
GOpening the watchlist (not measured yet)

The benchmark has not measured screen opening times yet (L2–L14 are empty), so this section has no today values. The code shows three things that add time on every visit to the Watchlist tab: the MTF list is awaited before the watchlist request starts, fixed 300 ms waits follow every sorted load, and a shimmer replaces the list on every visit even though the app-scoped cubit still holds the last list. These are worth fixing once L-timings exist to confirm the gain.

3 changes0 low · 3 med · 0 high
HWatchlist features and quick actions

The watchlist shows live price and change, holdings quantity and unrealised P&L, and offers Buy/Sell by swiping a row. Market depth, alerts and an order ticket open only on the full quote page, and rows have no mini chart. Both items are Product decisions first; the FE work reuses widgets that already exist in the quote module and stays behind a flag.

2 changes0 low · 0 med · 2 high
IThird-party SDK traffic on the watchlist

In 60 s on the idle watchlist the app contacted 9 third-party domains (Plotline, VWO, Google Firebase, CleverTap, MoEngage, Protectt.ai, AppsFlyer). Most of these SDKs are started for the whole app, not by this module, so the main item is a Product and BE decision. The watchlist itself mounts a Plotline banner and a Plotline-tracked kebab on every open, which is worth checking.

2 changes2 low · 0 med · 0 high
JCreation flow and accessibility

Creating Bench 20 showed a prefilled name that must be cleared, no confirmation when a stock is added, a header that shifts while the wealth tile rotates, and two icons that screen readers cannot name. These are small fixes; the visible ones are behind flags.

5 changes4 low · 1 med · 0 high
KTests and re-measurement

The fixes in sections A–C remove work that does not show on screen, so they can regress silently. These tests pin the behaviour: rows are not recreated on list updates, rows release their listeners, and the header state is emitted once per change. Re-measurement on the same phone closes the loop.

How to read this plan

Teams

FEFront-end change inside packages/trader_watchlist only. Owned by the module's FE team.
FE · sharedFront-end change in a shared package or the app shell. Other modules depend on these, so they need wider review and testing.
BEBackend, API, socket server, CDN or Remote Config value change. Needs the backend or platform team.
ProductChanges what the user sees or how a feature behaves. Needs a Product / UX decision before release. Until then the change ships behind a flag that keeps today's behaviour.

Risk to existing functionality

LowInternal to one widget or function. No visible behaviour change. Easy to revert. Normal code review and a smoke test.
MediumChanges loading order, timing, state flow or a visible detail inside this module. Needs a regression pass on the affected screen.
HighTouches a shared package used by other modules, navigation / back-stack, a live-data subscription model or the core state flow. Ships behind a feature flag and needs a full regression pass.

Effort

S≤ 1 day of work for one FE developer, including tests.
M2–4 days of work for one FE developer, including tests.
L1 week + of work for one FE developer, including tests.

Rules for not breaking existing functionality

  • One change per pull request, in the order of the risk waves on the Risk and rollout page.
  • Anything a user could notice ships behind a Remote Config flag whose default keeps today's behaviour. Product turns it on after sign-off.
  • Shared-package changes (FE · shared) are additive: new methods or parameters with today's defaults. No existing public API is removed or renamed in the same release.
  • Data, routes, analytics events and DI registrations stay the same unless the change says otherwise.
  • Every change lists its regression checks. QA runs them plus the screen's smoke test (open Watchlist tab, switch list tabs, scroll Bench 20, swipe Buy/Sell, tap a row to the quote page and back, list menu (Info, Sort, Manage), Manage Stocks, Create New Watchlist, add a stock from search, airplane mode on/off, background 60 s and return).
  • Re-measure on the same device after each wave and compare with the table above.
