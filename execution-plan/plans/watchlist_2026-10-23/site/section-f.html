Section F

Release logging and privacy

While the benchmark created Bench 20, the release build wrote the client code and analytics attributes to logcat, a doubled API URL, and an 'API Failed' line for a successful call. The code shows where each comes from: plain print calls in the CleverTap helper, a log line placed before parsing every API response, a URL built from an origin plus a path that is already a full URL, and a print of every cached response. The same paths also spend CPU converting whole responses to strings. These changes keep analytics and the app's own file log working but stop writing user data and noise to logcat.

Print CleverTap events only in debug builds

callCleverTap prints every event name and every attribute with print, which reaches logcat in release builds, including attributes such as Client Code. Wrap the prints in kDebugMode.

Teams FE · sharedRisk LowEffort S · ≤ 1 dayNo visible change

Today

callCleverTap calls internalLogClevertap(eventName, eventData) before CleverTapPlugin.recordEvent. internalLogClevertap uses print for a header, the event name and, via printAttributes, every key and value. Flutter's print writes to logcat in release. The search add-to-watchlist event includes ClevertapAttributes.clientCode: Preferences.getUserId() (trader_search search_clevertap_helper.dart 73-83), so the client code appears in logcat.

  3. Leave the dart:developer log() call (not printed in release).
